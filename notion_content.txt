# 1. 왜 만들었나 (스토리라인)



### 1막 — 계기

밤에 스마트폰을 늦게까지 보다 잠이 부족한 채로 등교하는 날이 반복됐다.  그러다 결국 늦잠을 자 지각을 하고 말았다. 그 뒤 지각을 안하려면 어떻게 해야하나 고민하게 되었다.


### 2막 — 조사

조사해 보니 나만의 문제가 아니었다. 한국 청소년의 평균 수면 시간은 약 5.8시간으로 OECD 국가 중 최하위이고, 중학생 52%·고등학생 90%가 권장 시간(8~10시간)에 못 미친다. 그런데 정작 잠이 부족한 학생 중 35%만 스스로 '부족하다'고 인식한다. 한편 청소년 스마트폰 과의존 위험군은 43.0%로 유일하게 증가 추세이고, 폰 사용 습관과 수면의 질은 서로 연결되어 있다.


### 3막 — 제작

"객관적으로 보여주는 도구가 없다면 내가 만들자." 매일 30초 만에 수면·폰 사용을 기록하면 AI가 내가 몰랐던 패턴을 짚어주고, 오늘 바꿀 수 있는 작은 습관 하나를 추천하는 웹앱 — 잠코치를 만들었다.

### 1. 작업 배경

  7/26에 DB 전환을 마치고 다음 계획으로 대시보드를 잡아뒀는데, 그 전에 급한 문제가 생겼다. 앱을 실제로 써보던 사용자(선생님, 회원 2호)에게서 "AI 코멘트가 매번 똑같다"는 피드백이 왔다. 그리고 전날 3시간 40분밖에 못 잤는데 앱이 "규칙적인 패턴을 만들어가는 중"이라고만 말하는 것도 문제였다. 통계는 맞았지만, 사용자는 앱이 자기를 보고 있다는 느낌을 못 받았다. 이 두 가지를 고치고, 예정됐던 대시보드까지 하루에 진행했다.
  

### 2. 진행 내용

  - AI 코멘트 캐시 수정 — 어떤 날짜의 기록이든 저장하면 오늘의 코멘트 캐시(sc_comment_)를 지우게 했고, 분석 화면에 "코멘트 새로 받기" 버튼을 추가했다.
  - AI 제공자 교체 — Gemini API에서 Cloudflare Workers AI로 옮겼다. env.AI 바인딩 방식이라 API 키 자체가 없다. 앱 코드(script.js)는 한 줄도 바꾸지 않았다.
  - 모델 순차 시도 — 특정 모델이 막혀도 앱이 죽지 않게 Llama 4 Scout → Llama 3.3 70B → Llama 3.1 8B 순서로 시도하고, 응답에 어떤 모델이 답했는지(model 필드)를 함께 돌려주게 했다. 응답에 한자가 섞이면 걸러낸다.
  - wrangler 설정 정리 — 이름을 my-worker에서 sleepcoach로 바꾸고, assets 설정을 제거하고, ai 바인딩을 추가했다.
  - 어젯밤 즉각 피드백 — 분석 화면 맨 위에 "어젯밤" 카드를 만들었다. 어젯밤 수면 시간, 평균과의 차이, 구간별 반응 문장을 보여준다. AI 프롬프트에도 어젯밤 기록(수면·폰·컨디션·낮 졸림)을 넣어 코멘트가 어젯밤에 먼저 반응하게 했고, 5시간 미만이면 "1시간 일찍 눕기" 미션을 우선 배정한다.
  - 분석 대시보드 — Chart.js로 최근 14일 수면 시간 막대 차트(8시간 기준선), 폰 사용 vs 컨디션 이중 축 차트, 이번 달 미션 완료율 카드를 추가했다. 달력 아래에는 "이달 기록 N일 · 평균 N시간 · 충분히 잔 날 N일" 월간 요약을 넣었다.
  - 달력 상세의 시각 표시에서 초 단위(00:20:00)를 제거했다.
  

### 3. 조사·학습 내용

  - Gemini API 약관이 만 18세 이상만 사용하도록 바뀌어 내 키가 막혔다. 처음 옮기려던 GitHub Models는 2026년 7월 30일에 서비스가 종료된 상태였다. 외부 서비스는 언제든 사라질 수 있다는 것을 처음으로 겪었다.
  - Cloudflare Workers AI는 바인딩 방식이다. 코드에 키를 적거나 환경변수에 넣는 게 아니라, wrangler 설정에 선언하면 런타임이 env.AI로 넣어준다. "키를 숨긴다"에서 "키가 없다"로 한 단계 올라간 구조다. 무료 한도는 하루 10,000 뉴런이다.
  - wrangler.jsonc에 assets 설정이 있으면 정적 파일이 먼저 응답한다. 그래서 POST 요청이 index.html 자산에 잡혀 405가 났고, worker.js는 실행조차 되지 않았다.
  - Chart.js는 같은 캔버스에 다시 그리기 전에 기존 차트를 destroy()해야 한다. 안 하면 탭을 오갈 때 차트가 겹친다.
  - 프록시 구조의 진짜 이점을 확인했다 — AI 제공자를 두 번 바꿨는데 앱 코드는 그대로였다. 7/5에 키를 숨기려고 만든 구조가 제공자 교체까지 막아줬다.
  

### 4. 문제와 해결 과정

  증상은 하나였는데 원인은 셋이었다. "AI 코멘트가 안 바뀐다"는 말을 듣고 처음엔 캐시라고 생각했다. 캐시 무효화 시점을 고쳤는데도 같은 문장이 나왔다. 화면의 문장이 코드의 예비 문장(fallback)과 똑같다는 것을 발견하고, Worker를 직접 호출해 봤더니 Gemini에서 400이 돌아왔다. 환경변수를 확인하니 GEMINI_API_KEY가 아예 없었고, 키가 나이 제한으로 막힌 것이었다. GitHub Models로 옮겼더니 이번엔 "retirement brownout" — 종료된 서비스였다. Workers AI로 다시 옮기고 배포했는데 405가 났다. GET으로 불러보니 Worker가 아니라 앱 화면(index.html)이 나왔다. wrangler의 assets 설정 때문에 정적 파일이 먼저 응답하고 있었다. 설정을 지우고 재배포하니 드디어 JSON이 나왔다. 그런데 한국어에 한자가 섞였고, 모델을 Gemma로 바꾸자 5018(이 계정에서 접근 불가) 오류가 났다. 그래서 모델 하나에 걸지 않고 세 개를 순서대로 시도하는 구조로 바꿨다.
  배운 것 — 증상 하나에 원인이 여럿일 수 있다. 의심 지점을 하나씩 배제하면서 범위를 좁혔고, Worker를 직접 호출해 앱과 분리해서 본 것이 결정적이었다. 그리고 예비 문장 덕분에 이 모든 과정에서 앱은 한 번도 죽지 않았다.

### 1. 작업 배경

  지난번 구글 로그인과 Supabase DB 연동으로 데이터 저장의 뼈대를 갖췄다면, 이번에는 사용자가 직접 마주하는 화면의 완성도를 높일 차례였다. PC 환경에서 화면이 가로로 넓게 퍼져버리는 현상, 스크롤을 내리면 하단 메뉴가 사라지는 불편함, 투박한 기본 입력 버튼 등 실사용 시 몰입을 방해하는 요소들이 있었다. 이를 개선하기 위해 전반적인 레이아웃을 다듬고 직관적인 커스텀 UI를 도입하는 'UI/UX 폴리싱(Polishing)' 작업을 진행했다.
  

### 2. 진행 내용

  - 날짜에 요일 표시: 달력에 써있는 날짜에 요일을 추가하여 평일/주말 수면패턴을 구분하기 편하게 했다.
  - 로그아웃 글자색 변경:기존에 검은색이라 배경색과 비슷해 구분하기 힘들던 로그아웃 글자색을 흰색으로 변경해 눈에 잘 띄게 했다.
  - 플로팅 하단 메뉴: 하단의 네비게이션 탭(기록/분석/미션/달력)에 position: fixed를 적용해, 스크롤 위치와 무관하게 항상 화면 하단에 떠 있도록 만들었다.
  - '낮에 졸렸나요?' 이해 쉽게 수정: 기존의 분리된 예/아니오 토글 스위치를 ‘예’와 ‘아니요’의 색을 바꾸고   옆에 현 상태를 써 이해를 쉽게 하였다.

  - 시간 기록 카드 화면 잘림 해결: '오늘 일어난 시각'을 입력하는 카드가 기기 너비를 초과해 잘리는 문제가 있었다. 이는 부모 요소의 여백(Padding)과 자식 요소의 width: 100%가 충돌해 발생한 문제로, CSS의 box-sizing: border-box 속성과 너비 비율을 적절히 조정해 컨테이너 내부로 깔끔하게 들어가도록 해결했다.
  - 슬라이더 UI 정렬 디테일: '자기 전 폰 사용 시간' 슬라이더에서 파란색 진행 막대가 회색 트랙 위로 붕 떠 보이던 현상을 겹치도록 수정했다.
  

### 3. 조사·학습 내용

  - 브라우저 캐시와 캐시 무효화(Cache Busting): CSS/JS 파일을 수정하고 배포했음에도 변화가 없을 때, 브라우저가 이전 파일을 기억하고(캐싱) 있기 때문이라는 것을 배웠다. <link href="style.css?v=9">처럼 파일 경로 뒤에 버전을 명시해 브라우저가 최신 파일을 강제로 다시 불러오게 하는 방법을 실무에 적용했다.
  - CSS Position의 이해: absolute는 부모 요소를 기준으로 위치를 잡지만, 화면 스크롤을 따라다니는 고정 메뉴를 만들 때는 뷰포트(화면)를 기준으로 하는 fixed 속성을 사용해야 함을 확실히 알게 되었다.
  - Webkit 커스텀 폼 요소: <input type="range">처럼 브라우저마다 생김새가 다른 기본 요소를 appearance: none;과 ::-webkit-slider-thumb 속성을 활용해 기획 스케치대로 완전히 새롭게 디자인하는 방법을 배웠다.
  

### 4. 문제와 해결 과정

  (1) 토글 스위치의 썸네일과 텍스트 위치 반전 문제 처음 구현한 토글은 썸네일(원)과 텍스트의 좌우 위치가 기획 스케치([ (O) 예 ])와 반대로 나오는 문제가 있었다. 일반적인 UI/UX 관례에 맞게, '예(활성화)'일 때 썸네일이 왼쪽으로 가고 '예' 텍스트가 오른쪽에 나타나도록 input:checked 상태에서의 transform: translateX() 좌표와 CSS left / right 속성을 완전히 반전시켜 해결했다.
  (2) 슬라이더 트랙과 진행 막대의 수직 정렬 어긋남 기본 Range 슬라이더 트랙 위에 별도의 파란색 막대(div)를 덧씌웠는데, 썸네일(20px)과 트랙(6px)의 높이 차이 때문에 기본적으로 트랙이 썸네일 중앙에 위치하게 되어 외부 막대와 어긋나는 현상이 발생했다. 이를 해결하기 위해 Range input의 기본 높이를 썸네일과 같은 20px로 강제 지정하고, 외부 막대의 top 위치를 여백(Padding)과 높이 차의 절반만큼 계산해 정확히 트랙 위치에 겹치도록 세밀하게 조정했다.
  (3) 노션 API 자동 업로드 권한 오류 (404 Error) 개발 일지를 노션 API로 자동 업로드하려 했으나 404 Object Not Found 에러가 발생했다. API 토큰은 유효하지만, 타겟이 되는 노션 페이지에 통합 앱(Integration)이 초대(Share)되어 있지 않아 접근 권한이 막혀 발생한 문제임을 확인했다.

### 2. 진행 내용

### 3. 조사·학습 내용

  - 브라우저 캐시와 캐시 무효화(Cache Busting): CSS/JS 파일을 수정하고 배포했음에도 변화가 없을 때, 브라우저가 이전 파일을 기억하고(캐싱) 있기 때문이라는 것을 배웠다. <link href="style.css?v=9">처럼 파일 경로 뒤에 버전을 명시해 브라우저가 최신 파일을 강제로 다시 불러오게 하는 방법을 실무에 적용했다.
  - CSS Position의 이해: absolute는 부모 요소를 기준으로 위치를 잡지만, 화면 스크롤을 따라다니는 고정 메뉴를 만들 때는 뷰포트(화면)를 기준으로 하는 fixed 속성을 사용해야 함을 확실히 알게 되었다.
  - Webkit 커스텀 폼 요소: <input type="range">처럼 브라우저마다 생김새가 다른 기본 요소를 appearance: none;과 ::-webkit-slider-thumb 속성을 활용해 기획 스케치대로 완전히 새롭게 디자인하는 방법을 배웠다.

  지난 시간에 구글 로그인을 완성했지만, 정작 기록은 여전히 브라우저 LocalStorage에만 저장되고 있었다. 로그인을 해도 폰과 노트북의 기록이 따로 놀았고, 기기를 바꾸면 기록이 사라졌다. "내 계정"은 생겼는데 "내 데이터"가 없는 상태였다. 그래서 이번에는 기록을 클라우드 DB로 옮겨, 어느 기기에서 로그인해도 같은 기록이 보이게 만들기로 했다.
  

### 2. 진행 내용

  - Supabase에 records 테이블을 만들었다. 기존 LocalStorage에 저장하던 항목(날짜, 잔 시각, 일어난 시각, 수면 시간, 폰 사용 시간, 컨디션, 낮 졸림)에 기록 주인을 표시하는 user_id 컬럼을 추가했다.

  - 같은 사람이 같은 날짜를 두 줄 만들 수 없도록 unique(user_id, date) 제약을 걸었다.

  - RLS 정책 4개(읽기·넣기·고치기·지우기)를 만들었다. 조건은 전부 auth.uid() = user_id, 즉 "지금 로그인한 사람이 기록 주인일 때만".
  - script.js의 저장·불러오기를 LocalStorage에서 Supabase로 전환했다. 로그인 상태면 DB, 비로그인이면 기존처럼 LocalStorage를 쓰는 이중 구조로 만들어 앱이 죽지 않게 했다.

  - 로그인 직후 기기에 남아 있던 기존 기록을 DB로 옮기는 이전(마이그레이션) 기능을 넣었다.
  로그인 이전 날짜의 기록들이 user_id가 붙은 채 DB에 들어와 있다 = 마이그레이션 성공
  - 좌측 상단 날짜를 누르면 달력이 열려 과거 날짜를 골라 기록할 수 있게 했다. 밀린 날짜를 몰아서 채울 수 있고, 미래 날짜는 선택되지 않게 막았다.

  - 하단에 [달력] 탭을 추가해, 한 달 수면 상태를 색 4단계(기록 없음·부족·보통·충분)로 보여주는 수면 달력을 만들었다. 처음 나온 화면이 밋밋해서 앱 전체 톤에 맞게 CSS를 다듬었다.
  

### 3. 조사·학습 내용

  - 데이터 저장에는 단계가 있다는 것을 배웠다. 변수(새로고침하면 사라짐) → LocalStorage(그 기기에만 남음) → DB(인터넷 어디서든 접근). 지금까지 앱이 2단계에 있었고, 이번에 3단계로 올라간 것이다.
  - SQL은 DB에게 시키는 말이고, 동사 네 개(insert 넣어줘 / select 골라줘 / update 고쳐줘 / delete 지워줘)가 기본이라는 것을 배웠다.
  - RLS(Row Level Security)는 기록 한 줄마다 DB가 검문하는 보안 장치다. 코드에서 "내 것만"이라는 조건을 안 써도 DB가 걸러주기 때문에, 코드가 실수해도 남의 기록이 새지 않는다.
  - using과 with check의 차이를 배웠다. 이미 있는 기록을 건드릴 자격을 보는 게 using(읽기·고치기·지우기), 새로 넣는 값이 규칙에 맞는지 검사하는 게 with check(넣기)다.
  - upsert는 update+insert로, 있으면 덮어쓰고 없으면 새로 넣는다. 테이블의 unique 제약과 한 쌍으로 작동해서, 같은 날짜를 다시 저장하면 줄이 쌓이지 않고 수정된다.
  

### 4. 문제와 해결 과정

  (1) 준비가 안 된 프로젝트에 SQL을 실행했다. Supabase 프로젝트가 아직 켜지는 중(Coming up)인 상태에서 테이블 생성을 진행해버렸다. 제대로 만들어졌는지 확신할 수 없는 상태가 됐다. 그래서 프로젝트가 Active로 바뀔 때까지 기다린 뒤, "현재 상태를 먼저 확인하고 없는 것만 생성하라"는 방식으로 다시 실행했다. 이미 있는 것을 중복으로 만들지 않으면서 안전하게 마무리할 수 있었다.
  (2) AI가 SQL을 직접 실행하지 못했다. Antigravity는 SQL을 만들어줄 수는 있어도 Supabase에 직접 실행할 권한이 없었다. 그래서 AI가 만든 SQL을 대시보드의 SQL Editor에 붙여넣어 직접 Run 했고, 실행 후 정책 조회 결과 표에서 정책 4개가 제대로 만들어졌는지(INSERT만 with check, 나머지는 using) 내 눈으로 검수했다. AI에게 맡기더라도 마지막 확인은 사람이 해야 한다는 것을 체감했다.
  (3) 캘린더 뷰가 못생기게 나왔다. 기능은 되는데 흰 바탕에 숫자만 있는 밋밋한 달력이 나왔다. 핵심인 "수면 상태 색칠"이 눈에 안 들어왔다. 기능은 그대로 두고 스타일만 바꾸라는 조건을 걸어 다듬었다. 잘 되는 기능을 건드리지 않도록 수정 범위를 못 박는 게 중요하다는 것을 배웠다.

  - 앱에 구글 로그인 버튼과 로그인 상태 유지 기능을 넣고, 배포해서 실제로 로그인이 되는지 확인했다. 내 계정이 이 서비스의 회원 1호가 됐다.
  

### 3. 조사·학습 내용

  - OAuth — 비밀번호를 우리 앱에 알려주지 않고, 구글이 대신 "이 사람 맞다"고 확인해주는 방식이다. 우리 앱은 비밀번호를 아예 다루지 않으니 더 안전하다.
  - 키의 두 종류 — Supabase에는 Publishable 키(코드에 넣어도 되는 공개 키)와 Secret 키(절대 코드에 넣으면 안 되는 비밀 키)가 있다. Secret 키는 .env 파일에 넣고 .gitignore로 막았다. 예전에 Gemini 키를 숨겼을 때와 같은 원칙이다.
  - Redirect URL — 로그인이 끝나고 돌아올 주소를 미리 약속해두는 것. 이게 정확하지 않으면 로그인 후 엉뚱한 곳에 떨어진다는 것을 이번에 몸으로 배웠다.
  

### 4. 문제와 해결 과정

  (1) 구글이 카드 등록을 요구했다. Google Cloud 콘솔에 처음 들어가자 카드 번호를 입력하라는 화면이 나왔다. 카드가 없어서 여기서 멈췄다. 당황했지만 화면을 자세히 읽어보니, 그건 유료 서비스 무료 체험 가입 화면이었고 내가 하려던 OAuth 클라이언트 발급과는 상관이 없었다. 그 화면을 닫고 다른 메뉴로 들어가니 카드 없이 진행됐다. 낯선 화면이 무엇을 요구하는지 먼저 읽고 판단해야 한다는 것을 배웠다.
  (2) 로그인은 되는데 404 페이지가 떴다. 구글 계정을 고르고 나면 잠코치로 돌아와야 하는데 404가 떴다. 처음에는 Supabase의 주소 설정이 틀린 줄 알고 Site URL과 Redirect URL을 몇 번이나 확인했지만 전부 정상이었다. 설정이 문제가 아니라면 코드라고 생각하고 살펴봤더니, 돌아올 주소를 만들 때 window.location.origin까지만 쓰고 있었다. 그러면 github.io까지만 나오고 뒤의 /sleepcoach/ 경로가 빠진다. 우리 앱은 하위 폴더에 배포돼 있어서 이게 문제였다. pathname을 붙이는 한 줄을 고치자 해결됐다. 설정부터 확인해서 정상임을 배제하고, 코드로 범위를 좁혀 원인을 찾은 첫 경험이었다.
  (3) AI 도구가 갑자기 멈췄다. 마지막에 코드를 GitHub에 올리는 작업을 Antigravity에 맡겼는데 에러를 내고 종료됐다. 다시 실행해도 되지 않았다. 그래서 예전에 배워둔 git 명령어를 터미널에 직접 입력했다. git add → git commit → git push 순서로 하니 그대로 배포까지 됐다. 도구가 멈춰도 원리를 알고 있으면 직접 할 수 있다는 것을 확인한 순간이었다.

### 3. 기획 — PRD 작성

  조사 결론을 바탕으로 PRD(제품 기획서)를 작성했다. 누구를 위한 앱인지, 무엇을 해결하는지, 성공 기준이 무엇인지를 한 장으로 정리했다.
  - 타깃 사용자 — 스마트폰을 늦게까지 보다 수면이 부족한 중·고등학생. 입력이 귀찮으면 안 쓰고, 잔소리를 싫어한다.
  - 해결 방법 — 하루 30초 기록 → 일주일 패턴 분석 → 오늘 할 수 있는 미션 1개. 잔소리 대신 데이터로 보여준다.
  - 성공 기준 — 3일 연속 기록이 이어진다 / 분석이 "몰랐던 패턴"을 하나 이상 짚어준다 / 미션이 실제로 해볼 만하다.
  

### 4. 기능명세서와 개발 체크리스트

  PRD가 "무엇을 왜"라면, 기능명세서는 "정확히 어떻게"다. 화면 3개(기록→분석→미션) 구조부터 입력 항목의 형태와 기본값, 분석 규칙, 예외 처리까지 적었다. 그리고 이걸 작업 단위로 쪼갠 개발 체크리스트를 만들었다.
  분석 규칙 4개도 이때 설계했다 — ① 주중 평균 수면 8시간 미만 ② 폰 많이 본 날과 적게 본 날의 컨디션 차이 1점 이상 ③ 취침 시각 표준편차 60분 이상(들쭉날쭉) ④ 낮 졸림 '예' 비율 50% 이상. 이 규칙 설계가 이 앱에서 내 생각이 가장 많이 들어간 부분이다. 조사에서 확인한 "폰과 수면의 연결"을 규칙 ②로 그대로 옳겨왔다.
  

### 5. 문제와 해결 과정

  넣고 싶은 기능이 너무 많았다. 수면 점수, 주간 리포트, 그래프, 친구와 비교 등 아이디어가 계속 나왔다. 전부 넣으려다가는 하나도 완성하지 못할 것 같았다. 그래서 "기록 → 분석 → 미션 한 줄이 작동하면 완성"이라는 MVP 기준을 세우고, 나머지(수면 점수, 주간 리포트, 상관관계 그래프, 미션 완료율)는 목록으로만 남겨 2순위로 미뤘다. 욕심이 미완성을 부른다는 것을 기획 단계에서 미리 배웠고, 이 기준은 이후 개발 내내 "지금 꼭 필요한가"를 묻는 잣대가 됐다.

## 🔧 기술

- 클라우드 조합 설계: GitHub Pages + Supabase + Cloudflare Workers + Gemini API를 조합해 서버 없이도 인증·DB·AI를 갖춘 실서비스 아키텍처를 구축했다.
- DB 설계 & 보안: 테이블 설계, RLS 정책, upsert 패턴 등 데이터베이스의 기본 개념을 실제 서비스에 적용하며 익혔다.
- 분석 알고리즘: 평균·표준편차·중앙값 기반 분류 등 수학적 논리를 코드로 구현하고, 엣지 케이스까지 고려하는 경험을 했다.


## 💪 태도

- 문제를 남이 정의해 주길 기다리지 않고, "청소년 수면 부족"이라는 사회 문제를 직접 조사하고 솔루션을 기획했다.
- 막힐 때마다 "안 된다"에서 멈추지 않고, 원인을 좁혀가며 끝까지 해결했다 (배포 404 디버깅, SQL 직접 실행 등).


## 🤖 AI 활용

- AI(Antigravity)를 "대신 만들어주는 도구"가 아니라 "같이 만드는 도구"로 활용했다.
- 기획·설계·분석 알고리즘은 직접 하고, 구현은 AI를 활용하되, AI가 만든 코드를 반드시 이해하고 검수한 뒤 수용했다.
- 예: RLS가 왜 select에 조건 없이도 작동하는지, upsert가 unique 제약과 어떻게 짝을 이루는지 직접 분석 후 Accept
